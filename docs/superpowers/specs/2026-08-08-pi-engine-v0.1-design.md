# PI-engine v0.1 Design

## Purpose

PI-engine v0.1 is a theory-neutral observational/predictive engine for representing structurally different systems in a common, inspectable form and testing explicit models against held-out outcomes.

The engine is intended to support later research into cross-domain invariants, multiscale structure, trajectory convergence/divergence, closure behavior, and hypothetical intervention analysis. Those higher-order hypotheses are not hard-coded into v0.1.

## Core design decisions

1. **Observational/predictive only in v0.1.**
   - No autonomous action.
   - No optimization of real-world interventions.
   - No controller authority.
   - Hypothetical intervention fields may be reserved in the schema for future compatibility but remain inactive.

2. **Explicit, inspectable model objects.**
   - Each model declares identity, provenance, applicability, variables, assumptions, equations/rules, uncertainty, expected signatures, falsifiers, and historical performance.
   - Models can remain contradictory.
   - Failed models are retained with evidence and failure regimes rather than deleted.

3. **Hybrid representation.**
   - State-space representation handles evolving scalar/vector variables, uncertainty, timing, phase, rates, and resource/energy-like quantities where meaningful.
   - Graph/topology representation handles nodes, edges, boundaries, relationships, effective proximity, geometry/topology, and coupling structure.
   - Both views refer to the same canonical case variables.

4. **Uncertainty is first-class.**
   Separate at least:
   - measurement uncertainty,
   - parameter uncertainty,
   - stochastic/process disturbance,
   - model discrepancy,
   - unknown/unmodeled residual.

5. **Prediction is an ensemble, not a single future.**
   - Preserve model-conditioned trajectory sets.
   - Support deterministic trajectories and stochastic/Monte Carlo ensembles.
   - Preserve branch/scenario probabilities or weights where justified.

6. **Closure is typed.**
   - Epistemic closure: uncertainty narrows because information improves.
   - Causal closure: reachable state-space narrows because system constraints or events actually change.
   - Provisional/soft closure: revisable assumption/constraint.
   - Hard closure: effectively irreversible or hard physical/logical constraint within the modeled domain.

7. **Invariant hypotheses are not schema requirements.**
   Candidate concepts such as Space, Time, Geometry, Energy, Relationship, Information, Phase, Proximity, 4+3+1, 7+1, nested octaves, or singularity/critical-state structures are annotations/hypotheses to be evaluated against outputs, never mandatory fields that force a match.

## Terminology alignment

Project language maps approximately to established controls/data concepts:

- Known baseline -> state / state estimate
- Observation -> measurement
- Watcher -> observer / state estimator
- Hidden variable -> latent/unmeasured state
- Glue/Web -> coupling + interconnection + information flow + phase relation
- Relationship -> topology / coupling
- Proximity -> effective interaction or model-space distance
- Future branch/timeline -> reachable trajectory / scenario
- Feedback -> innovation/update/receding-horizon feedback
- Closure -> feasible/reachable-state contraction or information-state contraction
- Unknown residual -> process noise, model discrepancy, or unmodeled residual depending on diagnosis
- Puppet master/+1 -> supervisory/orchestration function when embodied; otherwise may be distributed across closed-loop relations
- Nested eggs/octaves -> multiscale/hierarchical systems

## Canonical objects

### Case

A Case is the unit of prediction and evaluation.

Required conceptual fields:
- case_id
- title/domain
- source/provenance
- prediction_cutoff time or state
- observations available before cutoff
- canonical variables and units
- uncertainty declarations
- graph/topology
- state estimate
- applicable constraints
- withheld outcomes for evaluation
- hypothesis annotations (optional)

### Observation

- observation_id
- case_id
- timestamp/order
- variable
- value
- units
- uncertainty
- source/provenance
- quality/confidence metadata

### State

- timestamp/order
- observed components
- estimated/latent components
- uncertainty/covariance or equivalent confidence structure
- boundary/context variables

### Graph

- nodes
- edges
- edge direction
- coupling type
- coupling strength where justified
- effective proximity where meaningful
- geometry/topology metadata
- boundary relationships

### Explicit Model

Each model should contain:

**Identity**
- model_id
- version
- name
- domain/model family

**Provenance**

- evidence
- origin/author
- initial confidence

**Applicability**
- required variables
- optional variables
- valid ranges
- topology requirements
- boundary conditions
- exclusion rules

**Dynamics**
- equations/rules/transition functions
- time behavior
- deterministic/stochastic classification

**Coupling**
- relationships used
- phase dependencies
- effective proximity dependencies
- information dependencies

**Uncertainty**
- parameter uncertainty
- process noise/disturbance assumptions
- model discrepancy assumptions
- known unknowns

**Predictions**
- predicted variables/signatures
- prediction horizon
- expected regimes

**Falsification**
- falsifiers
- contradictory evidence conditions

- cases tested
- calibration metrics

### Trajectory / Scenario

- model_id

- initial state

### Outcome

- withheld observation(s) revealed after prediction
- comparison window
- source/provenance

### Residual

- predicted value/distribution
- observed outcome
- residual/error
- provisional classification:
  - noise-like
  - parameter mismatch
  - model mismatch
  - missing variable
  - regime change
  - coupling/topology error
  - phase/timing error
  - structured unknown residual

## High-level pipeline

1. Ingest/normalize case.
2. Validate provenance, units, cutoff, and no future leakage.
3. Build state-space and graph views.
4. Assess observability/identifiability limits.
5. Filter explicit model registry by applicability.
6. Run applicable models independently.
7. Generate deterministic and/or stochastic trajectory ensembles.
8. Analyze convergence, divergence, sensitivity, closure, and residual uncertainty.
9. Produce a prediction report preserving model disagreement.
10. Reveal held-out outcome.
11. Score forecast and model calibration.
12. Store residuals and update model performance metadata.

## Observability rule

The engine must be allowed to return:

> UNIDENTIFIABLE FROM AVAILABLE EVIDENCE

when multiple latent states or models cannot be distinguished using available observations.

Do not force a winner simply because ranking is required by a UI.

## Model selection / indexing

v0.1 uses an explicit registry and deterministic routing:

1. metadata/applicability filter,
2. structural compatibility scoring,
3. optional explicit similarity scoring,
4. ranked applicable model list.

Do not use a learned model router in v0.1. A learned-index/router may be introduced only after sufficient case data exists to benchmark it against deterministic routing.

## Testing and calibration

### Synthetic ground-truth systems

Provide systems with known dynamics, including at minimum:
- linear convergence,
- oscillatory dynamics,
- deterministic divergence/instability,
- stochastic branching,
- coupled oscillators,
- feedback instability,
- hierarchical/nested dynamics,
- random/no meaningful structure negative control.

Hide governing outcomes/equations from the inference/evaluation path as appropriate so recovery/prediction can be tested honestly.

### Temporal holdout

For documented time-ordered cases:
- expose information only through cutoff T,
- predict T+1..T+H,
- reveal withheld outcome afterward,
- repeat at multiple cutoffs where possible.

### Negative controls

Include:
- shuffled time series,
- random graphs,
- correlation without causal coupling,
- systems where proximity is explicitly irrelevant,
- systems lacking paired structures.

If the engine repeatedly detects favored structures in these controls, treat that as model/analysis failure.

### Calibration dimensions

Track separately:
- applicability confidence,
- parameter confidence,
- predictive calibration,
- structural confidence.

Avoid one opaque master confidence score.

### Proper probabilistic scoring

Initial scoring may include:
- absolute/RMSE-type errors for continuous deterministic outputs,
- Brier score for binary/categorical probabilistic outcomes,
- log score / negative log likelihood where distribution assumptions justify it,
- interval/coverage calibration for forecast envelopes.

### Cross-domain invariant promotion

Not implemented as an automatic v0.1 feature. Future promotion criteria should consider:
- coverage across independent domains,
- independence of source assumptions,
- held-out predictive gain,
- compression gain without accuracy loss,
- survival under falsification,
- necessity/ablation performance,
- scale persistence,
- reduction of structured residuals.

## Closure analysis

v0.1 should support descriptive detection/measurement of state-space contraction without making metaphysical claims.

Candidate measures may include:
- reachable-set size/volume proxy,
- trajectory ensemble spread,
- entropy/probability concentration,
- constraint activation count/severity,
- abrupt versus gradual contraction.

Any stronger interpretation such as literal multiverse collapse or consciousness-caused physical collapse is outside the engine's asserted conclusions and requires independent evidence.

## Future intervention compatibility

Reserve a future Intervention schema such as:
- variable/target
- proposed change
- timing
- duration
- confidence
- constraints

v0.1 must not execute, optimize, rank, or recommend interventions from this object. The core dynamics interfaces should simply be designed so a later counterfactual simulator can supply alternate inputs without rewriting foundational data models.

## Suggested technology stack

Keep v0.1 lightweight:
- Python 3.12+
- Pydantic v2 / JSON Schema
- NumPy
- SciPy
- NetworkX
- pandas
- pytest
- Hypothesis

Optional controls/optimization libraries may be added only when a concrete v0.1 model needs them.

Do not add PyTorch/TensorFlow or another ML framework for v0.1 model routing.

## v0.1 success criterion

Given several structurally different documented and synthetic systems, PI-engine can:

1. normalize them into the same canonical schema,
2. represent them simultaneously as state-space variables and relational graphs,
3. assess whether available evidence is sufficient to distinguish relevant states/models,
4. retrieve applicable explicit models with reasons,
5. generate deterministic and stochastic trajectory ensembles,
6. identify convergence, divergence, sensitivity, and closure signatures,
7. retain unexplained residuals rather than forcing them into favored models,
8. score forecasts against held-out outcomes,
9. preserve full provenance and model disagreement,
10. do all of the above without using Forged Codex labels or invariant hypotheses as mandatory inference inputs.

## Out of scope for v0.1

- Autonomous physical or software intervention.
- Real-time control authority.
- Intervention optimization.
- Learned/opaque model routing.
- Automatic invariant promotion.
- Treating 4+3+1, 7+1, Space/Time/Geometry/Energy, or similar hypotheses as established truths.
- Claims that the engine predicts literal alternate universes.
- Claims that consciousness/intention causes quantum collapse.
- Any probability score unsupported by explicit model assumptions and calibration history.
